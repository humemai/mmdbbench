# Republishing the project page

PROTOCOL.md says how a run is produced. FAIRNESS.md says what makes a comparison legitimate. READING-RESULTS.md says how to read what came out. This one says how the numbers get from the frozen rows onto the DBBench page of humem.ai (humem.ai/research/dbbench) without going wrong on the way.

## Where this fits

This file is the publish half of the routine, and the map of `results/` the publish reads from ("What is in `results/` and who reads it", below). The routine in order, both loops, is at the top of CAMPAIGN.md; read that first if you are new to it or returning after a campaign.

## The command

```
BENCH_ENGINE_COMMIT=<pin> python refresh_web_page.py
```

That is the whole routine. It regenerates the tables and figures into `results/generated`, exports the page data, runs the gates, syncs the JSON to `src/data/dbbench-benchmarks.json` in the humem.ai checkout, rewrites PAGE-SPEC.md's generated table inventory, builds the site, and prints the diff. The tables the page renders are the ones `src/lib/dbbench/lanes.ts` names by `tableId`; the lane pages reference no figure, so no figure is synced. It does not commit: reading the diff before publishing is the point, not an afterthought. When the comparators' chain was launched at a pin of its own (the 2026-11 comparator rows carry `e85469273`, not the page's pin), export `BENCH_COMPARATOR_PIN=<that commit>` as well (comma list); without it the failed and censored comparator cells lose their `envelope` and `censored` entries and `page_check` prints `MISSING` for them (below, "`BENCH_COMPARATOR_PIN` names the comparators' chain", humemai/mmdbbench#157).

Run it after **any** re-measure, after any change to the tables or figures, and after any change to the page's own table list.

Flags: `--site <path>` if humem.ai is not a sibling checkout; `--no-build` to skip the Next.js build (do not, normally: the build is what catches a page that names something the payload does not carry).

## The Engines documentation page

The Engines page of the documentation site (humemai/mmdbbench, `docs/engines.md`) is generated, never edited: `uv run python experiments/gen_engines_doc.py <path to docs/engines.md>` from the repo root. It reads the frozen 2026-11 rows (`make_paper_tables.load_canonical`), the arm names (`export_web.py`) and the override sentences (`override_registry.py`), so nothing on it is typed. Regenerate it at every landing and commit the result in humemai/mmdbbench; `--check <path>` exits 1 when it is out of date. Lanes and arms without rows yet are on its gap list.

## Which rows publish

The publish side renders rows stamped `instrument: 2026-11`, and nothing else. The freeze, the exporter, the gates, `land_stage.py` and `publish_results_asset.py` refuse a row of any other instrument, or a row with no stamp, with a message that says the tooling publishes 2026-11 rows only (`publish_instrument.refuse_other_instruments`; DECISIONS #196). If `BENCH_INSTRUMENT` is set to anything else, they refuse too; unset and `2026-11` mean the same thing here.

There is one freeze (`results/runs_paper.csv`), one payload (`results/web_benchmarks.json`) and one generated set (`results/generated`: `tables/`, `figures/`, `withheld_recall.json`, `io_stat_correction.json`, `GATE_STATUS.txt`). `BENCH_RESULTS_DIR` moves the whole `results/` tree and exists for tests only; a publish never sets it. The proof that the publish side works on 2026-11 rows is the fixture `fixtures/publish_2611` and two tests: `test_publish_2611_e2e.py` freezes and exports it end to end, and `test_publish_gates_2611.py` runs every gate below on the payload that comes out and requires each to pass. The fixture rows are copies of September and October measurements, so `build_fixture.realistic_2611` gives them what a 2026-11 row has and they lack (the override stamps, one pin, the roster of arms, the deep10m campaign rows behind the overlay files); its docstring names each patch and its reason, and `python build_fixture.py --patch` re-applies them to the committed rows. A gate that fails on the fixture is either right (the fixture row is one no 2026-11 run could write: fix the fixture) or still encodes a retired instrument (fix the gate).

Every ArcadeDB row measured under another pin is superseded, embedded as well as served; no ArcadeDB row is carried forward, and a comparator row carried forward is stamped `carried_forward_from` and `carried_forward_reason`.

## The one rule

> **Every page table is generated from frozen rows, listed in the manifest, pinned by `page_check`, and links its source.**
>
> Adapting a presentation is fine. A cell that traces to no frozen row is not.

This is PAGE-SPEC.md section 6.

## Why it is a script and not a checklist

A step done by hand from memory is a step that gets skipped. The script derives what to publish instead of being told: the exporter's output is the file the site gets, and the tables the lane pages name must match the tables the payload carries, so the page JSON cannot drift from what `export_web.py` produces today.

## What blocks a bad publish

The gate scripts (`refresh_web_page.GATES`), then three structural checks. All of them fail the run rather than warn:

| Check | Asks |
|---|---|
| `resource_check` | is any disk or memory value one that cannot be right: far below the other engines of its group (a group needs three engines, not three arms: ArcadeDB's embedded and served arms are one engine), a negative disk growth, or a disk reading taken after a failed pre-disk step (issue #349) |
| `provenance_check` | does every cell trace to a run, and does every paper-table cell rest on exactly 3 repetitions, what the 2026-11 instrument runs (`make_2611_stages --reps`, at most 3: the n=4 and n=5 passes were dropped on 2026-11-14; a row on any other count needs a disclosure in `caption_n.EXPECTED`); under `BENCH_ONLY_LANES` the repetition audit of the paper tables is skipped and the output names the lanes it did not check, so a landing without l4 is not refused for the time-series rows (a scope that names l4 still needs them in `make_paper_tables`) |
| `fairness_check` | F1 to F15 comparison invariants, durability class, instrument, and the stamps of the overrides a table discloses included |
| `equivalence_check` | do the engines of a table agree on the answer, and is every operation an engine cannot express declared (DECISIONS #88) |
| `page_check` | does the page agree with its own sources: its 9.99M dense cells with the generated table, the atomicity counts with the artifact, every operation of the query set a column with every engine answering or declared, no table losing its ArcadeDB row, every arm the 2026-11 subset owes a table on it as a row or a declared absence (the subset is `make_2611_stages`: an arm in `OUTSIDE` is owed nothing, the dense table owes its multipass-overlay arms, a payload that carries PQ rows owes the PQ arms whether or not `BENCH_DENSE_PQ=1` is set, and a table whose lane has no rows at this pin is not owed), and every number under a table traced to a source |
| `page_check.PROSE` | do the page's hand-typed prose numbers agree with the tables and the page-derived pins |
| `version_consistency_check` | does one engine wear two version strings across the page's tables (ArcadeDB: per size class, so the small and the large rows of a table may be on two releases), or a comparator an ArcadeDB release number |
| `version_pin_check` | do `runner.py`, `build_images.sh`, the three Dockerfiles, and COMPARATORS.md agree on every image digest and package pin (it reads no rows) |
| `_check_no_orphan_figures` | is every generated figure cited |
| refresh step 3, `tableId` coverage | does every table `src/lib/dbbench/lanes.ts` names by `tableId` exist in the payload, and does every table in the payload have a section on a lane page to render it; a scoped landing declares the tables it lacks in `pending_tables` instead of being refused |

The gates the procedure runs are the seven in `refresh_web_page.GATES`, plus `override_registry`, `degenerate_check` (on `runs_paper.csv`) and the two internal gates of `make_paper_tables` (`fairness_check` and `provenance_check` again, which print `GATES REPORTED FAILURES` and exit 0 unless `--strict`), then `make_paper_figures`. `claims_check.py` is a helper library and no gate: its default mode pins the typed numbers of the retired paper's prose to the rows behind them and cannot pass on any other rows; its `--regen` mode (do the committed tables regenerate from the rows) is the part a publish can use. `make_paper_figures` skips f3 with a printed reason when `results/sparse_cliff.jsonl`, a one-shot probe artifact of the retired instruments, is absent.

`PROSE` is its own check because the page's two surfaces fail differently. Cells are written by the exporter straight from the frozen results. Prose is typed by hand, so a wrong number in it is nearly inevitable.

A disagreement that has been reproduced, understood, and filed upstream prints as KNOWN rather than FAIL and its cell is withheld from the page instead of being published beside an answer it does not match (`equivalence_check.KNOWN_DISAGREEMENTS`, `export_web.WITHHELD_CELLS`); nothing is withheld today (`WITHHELD_CELLS` is empty). `KNOWN_DISAGREEMENTS` holds PostgreSQL + AGE's CRUD read-backs (apache/age#2587), whose cells publish with a note and are not withheld (DECISIONS #134). An entry is deleted at the re-pin that carries the fix, which re-arms the gate for that query, because a gate that cannot pass until an upstream release lands is a gate somebody deletes.

`WEB_ONLY_FIGURES` is the escape hatch for a figure the page shows and nothing else cites. It is deliberately empty; earn a line in it, do not assume one.

## Adding a table to the page

1. Confirm it is generated from frozen rows and add it to `export_web.LANES` or a builder in `export_web.py`.
2. Name it by `tableId` in a lane of `src/lib/dbbench/lanes.ts` in the humem.ai checkout, with its caption.
3. If it reports operations of the query set, add them to `page_check.OPERATION_MANIFEST`, so every operation is a column with every engine answering or declared. A table nothing checks can drift silently.
4. If the prose around it quotes any number, add each one to `page_check.PROSE` with a regex that captures the digits as printed. Quoting a number in a sentence is making a claim; a claim nothing pins is one nothing checks.
5. State in the table's conditions any measurement from the standard set it does not carry (PROTOCOL.md section 2, DECISIONS #89). `page_check` fails an omission that carries no reason.
6. Run the command above.

## What is in `results/` and who reads it

> **Which host.** This describes `results/` **on the bench host (mini)**, where the campaigns write. A developer checkout does not have the same tree: everything under `results/` is ignored by the allowlist at the end of the repo-root `.gitignore` (from `experiments/results/**`), which names the tracked artifacts one by one. Two consequences:
>
> 1. A path listed here may be absent from your checkout. That is expected, not a missing file. Check on mini before concluding anything is lost.
> 2. **Committing a path that exists untracked on mini makes mini's `git pull` fail.** Every queue script opens with `git pull -q --ff-only || abort` and has no clean-tree check, so the pull aborts the waiting stage. A modified tracked file does the same. An untracked file aborts the pull only once a commit adds that same path (git refuses to overwrite it); an ignored file at that path does not refuse, which is why the allowlist exists. Before committing anything under `results/`, check the incoming paths against mini's untracked files. A new tracked artifact needs `git add -f` and a line in the allowlist. Never `git add` a raw directory (`results/runs.jsonl`, `dense_mp5_*`, `sparse_mp_*`) and never `git add -A`: sweeping raw results into a commit is the other failure the allowlist closes.

**Rule: an output nothing reads may be deleted; superseded material that a decision still cites moves to `archive-<date>/` and keeps its name.** Quarantine markers (`QUARANTINE_`, `REFUSED_`, `SUPERSEDED_`, `NONCOMPARABLE_`) are evidence of a decision and are never tidied away.

### Order of operations, and it is not optional

A `runs_*_<pin>.jsonl` is the only copy of its data until it is merged. Archiving one before the merge deletes the campaign.

1. `merge_campaign.py`: campaign files into `runs.jsonl`
2. freeze: `runs.jsonl` into `runs_paper.csv`
3. `export_web.py`: into `web_benchmarks.json`
4. only then archive the campaign files, and only after confirming their rows are in `runs.jsonl` by `engine_commit`

`land_stage.py` performs steps 1 to 3 in one run (see "Landing a finished queue stage"); archive only after its pull requests are merged (it ends at PUSHED: `--apply` needs `--branch NAME`, pushes that branch of the bindings repo and of the site, never `main`, and prints the branch to open the pull requests from). A campaign file that shows "no reader" when you grep the publishing scripts is a file whose step 1 has not run yet, not a dead file.

The canonical store keys on `(lane, scale, n_docs, workload, backend, gav, rep, durability_class)` with the latest `ts_utc` winning, so a re-measured row supersedes the old one on merge. **Do not hand-edit the frozen CSV**; re-freeze after the campaign.

### The libraries the lanes import

No stage runs these directly, so a sweep for entry points finds no caller; each is imported, and none is dead (`grep` the module name for its importers): `bench_common.py` (statistics, run conditions, durability strings, answer digest), `graph_common.py` and `ldbc_snb.py`, `sparse_common.py` and `bigann_sparse.py` (the synthetic corpora and their real-data drop-ins), `budget_lookup.py` and `budgets.py` (query budgets; the table `derive_budgets.py` generates, never hand-edited), `arango_common.py`, `mongo_common.py` and `surreal_common.py` (per-engine connection and settings), `pagecache.py` (evicts a database from the page cache for a cold open), `l5_lifecycle_server.py` and `l5_lifecycle_surreal.py` (arms of `l5_lifecycle.py`), `lean_http.py` (the lean HTTP session behind the served ArcadeDB twin row, CAMPAIGN.md section 7, rows 72 and 82), `override_registry.py` (every override a table shows, PROTOCOL.md section 7), and `gen_engines_doc.py` (the Engines page, above).

The answer digest, the `durability` string, the thermal fields (BUGS.md F45), the idle-state stamps (`cpu_dma_latency_*`), `sparse_warmup_queries`, `dense_id_index` and `arcadedb_ts_result_format` are row fields, not files; print the row to answer a question about one.

`equivalence_check.py` and `resource_check.py` read the frozen set like the other gates and take `--rows <file>` for a campaign file or a smoke file. `equivalence_check` reduces to the newest row per cell first, so a re-run cell does not read as one backend giving two answers.

### Overlays: directories a table reads directly

| dir | feeds |
|---|---|
| `dense_mp5_<pin>/` | the page's 9.99M dense table, T5, and f4/f8's dense bars. Its pin is the one of the large class (below) |
| `dense_mp5_small_<pin>/` | the same table at 1M. Its pin is the landing's |
| `sparse_mp_<pin>/` | the warm columns on the page's `l3s` table (`export_web`). A tier is read from the directory of its size class: the `medium` files (the large size) at the pin of the large class, the `small` and `tiny` files at the landing's (below) |
| `e4decomp_<pin>/` | the E4 decomposition table: `export_web.py` (`E4_DIR`; it stops without the directory) and `make_paper_tables.py`. `land_stage.py` copies the `decomp3m_*.json` files into it, so a landing is blocked until the e4 lane has run at that pin. It is the small e4 size (`size_classes.SIZE_CLASS[("e4", "e2")]`), so its pin is the landing's |

Every other directory under `results/` is evidence, quarantine, or output; nothing generated reads it. Cache policy for the dense overlays: DECISIONS #56, disclosed in PROTOCOL.md section 7.

**All-or-nothing.** `make_paper_tables.dense_mp_dir()` is the ONE resolver for the dense overlays: it returns `results/dense_mp5_<BENCH_ENGINE_COMMIT>` only when every one of the 13 mandatory arms (`fp32 int8 arcsrv arcsrv_int8 milvus milvus_int8 qdrant qdrant_int8 chroma duckvss lancedb sqlitevec sqlitevec_int8`) has all `mp_<arm>_b<n>.json` files for the landing's build count, else it refuses. The count is three unless the landing says otherwise (n=4 and n=5 were dropped, 2026-11-14): `BENCH_MP_BUILDS=5` (or `land_stage.py --mp-builds 5`, which sets it) asks for five builds per arm, and a landing at n=3 needs no variable. `make_paper_tables.mp_builds()` is the one place that reads it; the refusals print the count they checked against, the page's "over N builds" follows the files, and a blank value means three. Only the number moves: an arm missing at any n still refuses, the directory is still pinned only with no fallback, and the directory name keeps `mp5` whatever the count (humemai/mmdbbench#27). `neo4jvec`, `pgvector`, `surreal`, `surrealsrv`, `arango` and `mongo` are optional arms (`MP_ARMS_OPTIONAL`) that join the table when all of their files exist (at the same count), are absent with none, and refuse the publish with some. `dense_mp5_small_<pin>` feeds the 1M tier with `MP_ARMS_SMALL`. T5, f4/f8's dense bars, the page's dense table, F4 in `fairness_check` and `provenance_check`'s `FEEDS` all call the one resolver, so they cannot disagree. A partial directory does not make a table visibly short (callers skip missing files), so without the rule a pinned export could ship a six-engine comparison as a single ArcadeDB row.

**Which pin a size class reads (humemai/mmdbbench#146).** `BENCH_ENGINE_COMMIT` is the pin of the run being landed and it is the pin of the small and the extra size classes: `dense_mp5_small_<pin>` is at that pin. The large class reads `BENCH_LARGE_ENGINE_COMMIT` when the landing names it, and the landing's pin when it does not (`size_classes.pin_of_size_class`, over the `SIZE_CLASS` table, which is the only classifier). Until the full benchmark of the large sizes (`export_web.LARGE_RUN_YEAR`) the large rows keep the numbers of 26.11.1 while the small rows move to 26.12.1, so the landing of 26.12.1 sets `BENCH_LARGE_ENGINE_COMMIT=a3a5d1245` (the 26.11.1 commit) or passes `land_stage.py --large-pin a3a5d1245`, which sets it: `dense_mp_dir()`, the 9.99M overlay, is then `dense_mp5_a3a5d1245`, kept in `results/`, and the exporter stamps its rows with that commit. A landing whose two classes are on one release sets nothing. Without the variable at the 26.12.1 landing the 9.99M overlay is not found, the large dense entries are rebuilt from the lane rows and lose `warm p50 ms` and `warm p99 ms`: `export_web.py` refuses to write the payload then (`large_entry_gate.refuse_lost_large_keys`), because a large dense entry that had an overlay key in the payload on disk, the page as last published, and has lost it, or is gone, is a loss and not a change. The sentence names the table, the entry and the keys. When the large sizes are rerun, their overlay is at the new pin and the variable is dropped. The sparse overlay follows the same rule per tier (humemai/mmdbbench#151): `export_web._sparse_multipass_table` reads each tier from `sparse_mp_<pin>` at the pin of the tier's size class (`SIZE_CLASS[("l3s", tier)]`: `medium` is large, `small` is small, `tiny` is extra), so at the landing of 26.12.1 the medium files are in `sparse_mp_a3a5d1245` and the small and tiny files in the landing's directory, and the medium entries carry the 26.11.1 commit. The gate holds the large `l3s` entries to the keys the second pass supplies (`warm p50 ms`, `warm p99 ms`, `gain`) as it holds the dense ones. `e4decomp_<pin>` holds the small e4 size and is read at the landing's pin. The landing also runs `make_paper_tables.py` and `make_paper_figures.py` (`refresh_web_page.py`, step 1), and their readers follow the same rule (humemai/mmdbbench#154): `make_paper_tables.sparse_tier_pin(tier)` is the pin of a sparse tier (`pin_of_size_class` over `SIZE_CLASS[("l3s", tier)]`), `_pinned_sparse_rows` freezes each tier's rows at it and holds one engine identity per pin (so the small tiers on 26.12.1 and `medium` on 26.11.1 freeze), `make_paper_figures._sparse_overlay_pass` reads `sparse_mp_<that pin>`, and `export_web._censored_cells` reads each row of the run log at the pin of its own size class (`size_classes.row_size_class`), so a timeout of a large cell at the old pin keeps its note. A sparse tier with no row at all at its pin is absent, a dash on the table and in the figure and nothing to refuse (the rerun of 26.12.1 is the small sizes only and the store has no `l3s` row at the 26.11.1 commit, so `medium` has none at either pin; humemai/mmdbbench#157); a tier with some rows and fewer than the landing's build count is partial and refuses, and so does a tier whose only rows are at another commit, with the sentence that names `BENCH_LARGE_ENGINE_COMMIT` and `land_stage.py --large-pin` (the shape of a forgotten large pin; the refusal of a freeze that holds both builds says it too); an arm with no rows at the landing's own pin is absent (`{}`), so a staged landing that holds only the carried 26.11.1 rows is not refused before the sparse stage of the new release has run. One release for both classes needs no variable and nothing moves.

**A served ArcadeDB arm's overlay file carries its client** (humemai/mmdbbench#62). A served ArcadeDB cell runs as up to three jobs: the vendor driver, the lean twin and, at the small tier, the PostgreSQL-wire twin. In the 26.11.1 campaign all three wrote one name (`mp_arcsrv_b<n>.json`), the last job to finish kept the file, and the lean files of the n=3 pass were lost. The runner now writes one file per client: `mp_<arm>_clientlean_b<n>.json`, `mp_<arm>_clientofficial_b<n>.json` and `mp_<arm>_clientpgwire_b<n>.json` (the sparse overlay: `sp_<arm>_clientlean_<tier>.json`; the native chain keeps `_native` after the client). The arms with no client axis (the comparators, the in-process arms) keep `mp_<arm>_b<n>.json`. Every reader asks for the plain name through `overlay_merge.files()` or `overlay_merge.pick()`: it gets the file named for the lean client when there is one, else the plain file, so the 26.11.1 directories read as before, and it never gets a file named for another client. A plain file beside a lean-named one follows the merge rule of `overlay_merge` (#61): the same bytes are fine, a plain file that names the vendor driver or the PostgreSQL wire loses, anything else refuses. `land_stage.py --overlay <arm>` pulls the plain and the lean-named files, `--overlay-merge` leaves the files named for the other two clients out and lists them in `MANIFEST.txt`, and `export_web._refuse_other_client_overlays` still refuses a file a table reads whose rows name the vendor driver.

### Evidence and quarantine, kept deliberately

| pattern | why it exists |
|---|---|
| `NONCOMPARABLE_*` | a run whose conditions do not match the tier it looks like it belongs to |
| `QUARANTINE_*` | rows stamped with conditions they did not run under |
| `REFUSED_*` | rows a lane guard rejected |
| `SUPERSEDED_*`, `*.SUPERSEDED-*`, `*.prequarantine` | the file as it stood before a known defect was fixed |
| `delta_scan_<pin>/`, `ablation_cache_<pin>.jsonl`, `verify_<sha>/` | upstream evidence. Not page inputs; `ablation_cache` is read only by `dense_matrix.py`, the operator table, and is never merged into `runs.jsonl` |

**When adding a result directory,** add it to `FEEDS`/`FEEDS_FILES` in `provenance_check.py` **or** to this section. The audit exists to catch an unaudited input to a published cell; every entry it prints that is actually fine makes the next real one easier to miss.

**`evidence/`** holds tracked copies of what an upstream report cites: `results/` is untracked by design, but an upstream issue needs a stable URL. Copy, never move; `results/` stays the working store.

**Queue scripts.** The live chain and where finished scripts go: CAMPAIGN.md section 6; what each stage runs: `make_2611_stages.STAGES`. Every script gates on `verify_pair_c25.sh`, which sits here beside `build_matched_pair.sh` and `build_c25_wheel.sh`, the pair recipe.

## Landing a finished queue stage

One command, the same order every time, refuses by default:

```
BENCH_COMPARATOR_PIN=<commit the comparators' chain was launched with> \
.venv/bin/python experiments/land_stage.py \
    --pin <commit of the run being landed> \
    --only-lanes <lanes the stage measured, comma list> \
    --exclude-backends <backends still running on mini, comma list> \
    [--overlay neo4jvec] [--large-pin <commit of the release the large rows are on>] [--exclude-since <stage ALL-DONE timestamp>] \
    [--drop-unless arcadedb_graph_server:l2:oltp:server_http_body_max_bytes=68719476736] \
    --message "<one line: what joined>" [--dry-run | --apply]
```

It pulls `runs_page_<pin>_2611.jsonl` (and, with `--overlay`, an arm's dense multipass files at both sizes, always the sparse second-pass files `sparse_mp_<pin>/` when the sparse lane lands (BUGS F148), and always the deployment decomposition's `e4decomp_<pin>/` files, since the `e4` table is a directory of artifacts rather than rows in the log and the export stops without it), drops the rows of the backends named as still running so a stage in progress never reaches the freeze, merges, publishes through the gates, and prints which page tables changed.

**`--drop-unless` drops the rows a repair stage replaced.** `BACKEND:LANE:WORKLOAD:FIELD=VALUE` drops that cell's rows whose FIELD is not VALUE (absent counts as not VALUE), so the old rows go and the repair's rows, which carry the stamp, stay; repeat it for several cells. Example: the spec in the command above keeps, for ArcadeDB's served graph OLTP, only the rows that carry the raised bulk-load body limit stamped as `server_http_body_max_bytes` (DECISIONS #172). A malformed spec ends the run instead of dropping nothing.

**`--only-lanes` scopes a staged landing, and the scope is cumulative.** Rows of every lane not named stay on the host for a later landing, because the gates read the whole freeze and would fail a landing on lanes it was not publishing; empty lands everything. The scope is the lanes named PLUS every lane already on the page, read from the published payload, so a landing adds to the page rather than rebuilding it (BUGS F111; PAGE-SPEC.md section 2). A landing that would make any table on the page disappear is REFUSED and the site's payload restored. After the merge it also WARNS, without refusing, when a landed lane's rows were measured before a later commit to that lane's own script, and lists the commits. Without `--apply` it stops there and restores the site's payload; with `--apply` it builds the site, commits both repositories, and pushes. The merge into `runs.jsonl` is idempotent, so a run without `--apply` followed by one with it is the normal sequence.

**`--apply` governs the PUBLISH, not the merge, and `--dry-run` is the flag that writes nothing.** A run without `--apply` still performs steps 2 and 3, and step 3 merges. `--dry-run` pulls, filters, and stops: it prints how many rows WOULD merge and which of them carry errors, and leaves `runs.jsonl` byte-identical. It is also the mode a pre-campaign rehearsal wants.

**The pulled file is screened before it is merged, and a rehearsal can run on scratch copies.** `screen_pulled_rows` refuses the whole file, before `--exclude-*` and before the merge (so `--dry-run` shows the refusal too), when any row is not stamped `2026-11` (a retired 2026-10 file, a mixed file, an unstamped row) or names an engine commit other than `--pin` (prefix either way); nothing reaches `results/runs.jsonl`. The first landing creates the store. Failed cells (`rc != 0` or an error) are reported and merged as failures, and the freeze skips them; censored queries are reported and keep their flag. `BENCH_LAND_SITE` moves the humem.ai checkout (the landing passes it to `refresh_web_page.py --site`), `BENCH_LAND_PY` the interpreter every step runs under, `BENCH_LAND_HOST`/`BENCH_LAND_REMOTE` the bench host and `BENCH_LAND_SCRATCH` the pull directory, so a rehearsal never writes the real site checkout. A landing scoped away from e4 does not need `e4decomp_<pin>`, and that holds at the first landing of a new pin too: before the pull the landing reads which lanes the page already carries by importing the exporter in its own process, and it hands that import the landing's `--only-lanes` as `BENCH_ONLY_LANES`, so the exporter's refusal for a missing `e4decomp_<pin>` applies only to a scope that names `e4` and to no scope at all (humemai/mmdbbench#147; before the fix the import had no scope, and the first scoped landing at a new pin ended with `e4decomp_<pin> missing` and rc 1 before any pull). A refusal of the exporter at that import is printed with its own words, the scope and the pin it saw. A scope that names `e4` needs `e4decomp_<pin>/` in `results/` before the run, because this read comes before the pull.

**`BENCH_LAND_PULLED_FILE` lands rows that were pulled elsewhere.** The four-arm chains write their rows into several results directories on the bench host, so no single `scp` has them all. Set the variable to a merged rows file and step 1 copies it in place of the `scp`; the screen, the filters, the merge and the gates then run on it as on any pulled file. A path that is not a file ends the run, it never falls back to the host. Unset, the landing pulls from the host as before. `tools/merge_fourarm_rows.py` builds that file from the four places the four-arm rows live (`tools/CHECKS.md`).

**`--overlay-merge` builds the dense overlay of one landing from several sources, and `--overlay-exclude` can name the source it leaves an arm out of.** `--overlay-merge LABEL:PIN:DIR` (repeatable) merges `dense_mp5_<PIN>` and `dense_mp5_small_<PIN>` of the local directory DIR (also with the host's `_2611` suffix) into `results/dense_mp5_<pin>` and `results/dense_mp5_small_<pin>`; the directory the landing already holds is a source too, labelled `existing`, and one file name with different bytes refuses (`overlay_merge.py`). `--overlay-exclude ARM` leaves an arm's files (JVM and native) out of every source. `--overlay-exclude ARM@LABEL` leaves them out of the one source called LABEL (as in `--overlay-merge`, or `existing`) and keeps them from the others; a LABEL that names no source refuses. The case it is for: the overlay of the old pin holds the comparators and ArcadeDB's old arms, the overlay of the new pin holds ArcadeDB's new arms, and both hold `mp_fp32_*` and `mp_arcsrv_*`. Without an exclude the merge refuses on the name collision, and a global `--overlay-exclude fp32` takes the new files out with the old ones. `--overlay-merge old:<oldpin>:<dir> --overlay-merge new:<pin>:<dir> --overlay-exclude fp32@old --overlay-exclude arcsrv@old` keeps the old comparators and the new ArcadeDB arms (humemai/mmdbbench#147; `test_overlay_merge.py`).

**`--large-pin` names the release of the large rows, and the landing reads the large overlays at it (humemai/mmdbbench#151).** Until the full benchmark of the large sizes, a landing of a new release has its small rows at the new pin and its large rows at the old one, so the overlays of the large size sit in directories named by the old pin. `--large-pin <commit>` (default `BENCH_LARGE_ENGINE_COMMIT`, else `--pin`; a landing whose two size classes are on one release needs no flag and nothing moves) sets `BENCH_LARGE_ENGINE_COMMIT` for every step, and a flag given wins over a variable already set. The landing then pulls an `--overlay` arm into `dense_mp5_<large pin>` (9.99M) and `dense_mp5_small_<pin>` (1M), each from the host directory of its own pin, so no empty `dense_mp5_<pin>` is made for the large size; `--overlay-merge` builds `dense_mp5_<large pin>` and `dense_mp5_small_<pin>` (each source is still read at its own `PIN`); the sparse second pass is pulled as the `medium` files from `sparse_mp_<large pin>_2611` into `results/sparse_mp_<large pin>/` and the `small` and `tiny` files from `sparse_mp_<pin>_2611` into `results/sparse_mp_<pin>/`; and `e4decomp_<pin>` stays at `--pin`. Every landing from 26.12.1 on passes `--large-pin a3a5d1245` (or has the variable set) until the large sizes are rerun, a catch-up or a scoped landing included, because the exporter rebuilds the whole page each time. Without it the exporter refuses to write a page whose large dense or large sparse entries lost their warm columns, and the sentence points at this flag (`large_entry_gate.py`, `test_sparse_large_overlay_by_release.py`). A forgotten flag is caught earlier than that (humemai/mmdbbench#157): before anything is pulled, merged or written, a landing with no large pin (neither the flag nor `BENCH_LARGE_ENGINE_COMMIT`) refuses when the published page holds a large-size ArcadeDB entry at a commit other than `--pin`, names that commit and says `--large-pin <commit of the large rows>`. A landing of large rows that were rerun at the pin says so with `--large-pin <pin>`. No payload yet (the first landing) is not refused.

**`BENCH_COMPARATOR_PIN` names the commit the comparators' chain was launched with (humemai/mmdbbench#157).** The comparators and ArcadeDB are two chains and two rows files, and the comparator rows carry the comparators' own pin (`e85469273` for the 2026-11 rows), which is neither the page's pin nor the large pin. `export_web._censored_cells` keeps a row of the run log only at the pin of its size class (`size_classes.row_at_pin`: the landing's pin, the large pin for a large size) or at a commit named by `BENCH_COMPARATOR_PIN` (comma list). With the variable unset the failed and censored comparator cells (DuckPGQ at `sf1` and `sf10`, SurrealDB at `sf1full`) were dropped without a word, the payload lost their `envelope` and `censored` entries, and `page_check` printed `MISSING` three gates later. So export it before `land_stage.py`; the landing hands it to every step. After the screen and before the merge (on `--dry-run` too) the landing reads the store and the rows about to merge, and refuses when a failed comparator row (an `error`; rows of the publishing instrument, in the landing's scope) is at a commit that is none of the pin of its size class and `BENCH_COMPARATOR_PIN`: it names each commit with its cell count and the first cells, and the variable to export. The same variable tells the sparse pull where the comparators' chain wrote its files (below).

**Two chains, one pin, one landing.** The JVM chain and the native chain of a rerun write into two worktrees of the bench host but are built at one engine commit, so they share one pin and land together: two pins cannot land at once (`screen_pulled_rows` refuses a row whose commit is not the pin, and one `BENCH_ENGINE_COMMIT` keys every overlay). `land_stage.py` reads each input from one place, so prepare the landing like this (humemai/mmdbbench#147):

- Rows: `tools/merge_fourarm_rows.py --pull <pin> --worktrees <jvm worktree>:<native worktree> --out FILE` (`BENCH_FOURARM_RESULTS` names the results directory below the worktrees when it differs from the default), then land with `BENCH_LAND_PULLED_FILE=FILE`. The default `BENCH_LAND_REMOTE` is the results directory of the host's main clone, not of the chains' worktrees, and `merge_fourarm_rows.py` merges rows only.
- Sparse second pass and e4: the pull takes `sparse_mp_<pin>_2611/sp_*.json` and `e4decomp_<pin>/decomp3m_*.json` from that one directory. The JVM files (`sp_<arm>_<tier>.json`) and the native ones (`sp_<arm>_native_<tier>.json`) sit in different worktrees, and `e4decomp_<pin>/` only in the JVM one (`arcadedb_e4` has no native counterpart). Create `experiments/results/sparse_mp_<pin>/` and `experiments/results/e4decomp_<pin>/` before the run and copy into them the files of both worktrees, the union. The two `scp` calls are `check=False` and a directory that already holds files is kept as it is, so the pull adds nothing and the landing reads the union (`test_land_stage_2611.py`). With a `--large-pin`, the medium files of the union belong in `experiments/results/sparse_mp_<large pin>/` (below). The comparators' chain is a third source (humemai/mmdbbench#157): it writes `sparse_mp_<its own pin>_2611/` (`sp_qdrant_*`, `sp_pgvector_*`, `sp_qdrant_uint8_*`), and with `BENCH_COMPARATOR_PIN` set the pull also copies the files of that host directory that are not ArcadeDB's into the directory of their tier's class (`sparse_mp_<pin>` for `tiny` and `small`, `sparse_mp_<large pin>` for `medium`). An `sp_arc_*` file of that directory is never copied (it is an older release's), and a file the landing already holds wins, so a copy by hand stays what it was. Milvus and Elasticsearch are outside the 2026-11 subset (`make_2611_stages.OUTSIDE`), so no chain of the rerun writes `sp_milvus_*` or `sp_elastic_*`. A small tier therefore requires the arms the rerun runs (`arc_int8`, `arc_fp32`, `arc_srv`, `qdrant`; `pgvector`, `qdrant_uint8` and `arc_srv_fp32` stay optional) and a missing file of one of them refuses with the file named; `elastic` and `milvus` (`export_web.SPARSE_MP_BY_PRESENCE`) are required only when some file of the arm exists, all or nothing. With none, the `l3s` table says "Elasticsearch was not run at this release." (and the same for Milvus) and declares the absence (kind `not measured`, whole row), with no reason, because none was recorded.
- Dense overlays: `--overlay ARM` pulls from the one host directory too. For two worktrees copy each one's `dense_mp5_<pin>_2611` and `dense_mp5_small_<pin>_2611` into a local directory and land with `--overlay-merge jvm:<pin>:<dir> --overlay-merge native:<pin>:<dir>`; the JVM files (`mp_<arm>_b<n>.json`) and the native ones (`mp_<arm>_native_b<n>.json`) have different names, so nothing collides.

The e4 directory is pulled under the name `e4decomp_<pin>`, without the `_2611` suffix that the rows file and the sparse and dense directories carry. That is the name `e4_decomp.py` writes (`results/e4decomp_<pin>/decomp3m_<pin>_rep<r>.json`) and `export_web.py` reads, so the pull is right and the name stays. `land_stage.py` does not take a list of remotes: each input would need its own rule for a file present in two of them, and the rows already have one (`merge_fourarm_rows.py`).

**The native files and the `tiny` files are owed by the rows, and the files are checked before the merge (humemai/mmdbbench#160).** A table entry takes its warm columns from the overlay file, so a native row whose overlay file is missing printed without them (the `l3s` entries) or left the page (the `l3d` entries), with every gate green. The rule is one helper, `native_overlay.py`, read by the sparse and the dense table: when the frozen rows hold a native-build ArcadeDB row of an overlay arm at a size, the overlay of that size must hold the arm's native files (`sp_<arm>_native_<tier>.json` for the sparse tiers, `mp_<arm>_native_b<k>.json` for the dense small size) and a missing one refuses with the file named. A native file is owed per arm, so an arm the native chain did not run owes none, and a table with no native rows owes none. The `tiny` tier of `l3s` owes the same plain files as `small` when the rows hold an `l3s` row at that size; a tier with no row and no file is still absent. The 9.99M dense overlay is not held to native files (its native served arm has no overlay and is read from the lane rows; the large-entry gate covers its warm columns). After the pulls and before the merge, `land_stage.py` lists the sparse and dense overlay files the exporter will need for the scope and the pins (`export_web.sparse_files_owed` and `dense_files_owed`, the exporter's own lists, read from the directories that are there: an absent directory is a lane that has not run), and refuses with the missing files and the step that makes each: the ArcadeDB union of the two worktrees, the comparators' chain (`BENCH_COMPARATOR_PIN`), or `--overlay-merge`. A `--dry-run` prints the same list as `WOULD REFUSE` and stops as it always does, with rc 1 (humemai/mmdbbench#163: a script that runs a dry run first sees the refusal in the exit status); a dry run with no missing file exits 0. A scope without `l3s` and `l3d`, or an exporter that cannot be imported for the scope (no `e4decomp_<pin>/` yet), is not checked and the check says nothing. The log prints that an `scp: No such file or directory` line for the sparse, medium and e4 directories is expected when the host does not hold them, and the comparator line says when the landing already holds the host's files. The first read of the landing, which imports the exporter for the published lanes, refuses a scope that names `e4` when `e4decomp_<pin>/` is not in `results/`, and says to copy the host's directory there first: that read comes before the pull, so the pull cannot fill it for a first landing of the pin (`test_silent_overlay_losses.py`).

**The native server image needs an entry in `engine_commit_equiv.json` before its rows land (humemai/mmdbbench#160).** Upstream builds the `-native` server image at the release tag, one commit after the commit of the JVM image, the jars and both wheels, so a served native row reports a commit that is not the pin. `experiments/engine_commit_equiv.json` holds the pair per release, and without the entry of the release being landed (`26.12.1`) the landing stops in step 4, after the merge into the store, with one sentence per served arm (`the native server reports engine commit <x> and the row names <pin>`), and the exporter now ends that refusal with the registry and the generator. The entry is never typed: `make_engine_commit_equiv.py --repo <engine checkout> --base <pin> --head <commit of the release tag> --release 26.12.1 --old-release 26.11.1 --out-md ENGINE-COMMIT-EQUIV-26.12.1.md --out-json <file>` computes it from the git diff and writes it only when the two commits differ by version strings alone and by exactly one commit (it refuses any other diff). It writes an object with one key, the release, and the registry holds one key per release, so the object is merged by hand into `engine_commit_equiv.json` and committed in its own pull request before the landing. `HARNESS_SHA` (`make_2611_stages.py --harness-sha`) moves after: the stages run from the checkout pinned at it and read the registry there, so the pin is a commit that holds the entry, and the drafts of the chains are generated again with it. `land_stage.py` step 6 commits `experiments/engine_commit_equiv.json` with the other tracked artifacts (`land_stage.tracked_artifacts`), so an entry that was changed after the branch point is not left behind.

**A failed or missing small cell is named before the merge.** After the filters and before the merge (on `--dry-run` too), the landing lists every ArcadeDB cell of the small size class (`size_classes.SIZE_CLASS`: lane, scale, workload, arm and build) that has a repetition with no `rc=0` row at the pin. It reads the store and the rows about to merge, within the landing's scope and repetitions 1..`--max-rep`. The freeze drops a failed row before it keeps the newest row of a key, so such a repetition keeps its row of the older release, and the pair gate (`arm_identity.pair_problems`) then refuses the size class with the tables named, not the cell. For each repetition the block says whether a row at the pin failed (with its `rc`) or there is none, and which older row the freeze keeps. It is a warning and not a refusal: an arm the rerun leaves out on purpose is listed too, and whether the cell is owed is the reader's call. The gates and their messages are unchanged (humemai/mmdbbench#147).

**`--max-rep N` lands repetitions 1..N only, and N is 3 unless the flag says otherwise.** The comparator pass 4 started once on the bench host before the n=4 and n=5 passes were dropped (2026-11-14, DECISIONS #335 in the private notes), so the same `runs_page_<pin>_2611.jsonl` holds a few rep 4 rows that must never land: a landing at n=3 needs no flag (`--max-rep 3` is the default; `--max-rep 0` is the explicit opt-out that lands every repetition as pulled): rows of a later repetition are left out before the screen, the filters and the merge, and the count per dropped repetition is printed. A row whose `rep` is not an integer ends the run, naming the row number, its run id and the file, by default too (`test_land_stage_max_rep.py`).

**`--pin` is given, with the flag or with `BENCH_ENGINE_COMMIT`, on every landing.** Step 1 pulls the stage's rows file by exact name, so a wrong pin fetches the wrong rows and fails much later, with the merge already done; pass `--pin <commit>` or set `BENCH_ENGINE_COMMIT` on every landing. There is no other default (humemai/mmdbbench#157). The landing used to take the one commit the current payload names, and that is the build already published: before the first landing of a new release it is the OLD commit, so a landing started without `--pin` pulled `runs_page_<old pin>_2611.jsonl` and merged the old rows again, with no refusal. It now refuses and says which commit the payload names. A payload that holds two commits (the small rows of a table on a new release and its large rows on the old one) never had a single pin to offer, because `arcadedb_commits` is a sorted list that does not say which one is newer (humemai/mmdbbench#147).

Never `git add` a raw directory under `results/` (see the first note of the results section above).

## The data behind the page, as a release asset

`publish_results_asset.py --tag <tag>` bundles `results/runs_paper.csv` and `results/web_benchmarks.json` with a manifest naming the engine pin, the tables, the row count, the file checksums, and the gate status, and attaches it to a GitHub release with `--publish`. It refuses a freeze or a payload that holds a row of another instrument. Without `--publish` it writes the bundle and prints what it would upload, the same dry-run-then-apply shape `land_stage.py` uses. Most readers who doubt a benchmark want the rows rather than a way to rerun it (DECISIONS #97). Run it after a campaign is frozen, not after every stage.

## Moving to the next instrument

A new instrument arrives under the same names. Its rows carry its label in `instrument`, `publish_instrument.PUBLISH_INSTRUMENT` moves to that label in the same change that freezes them, and the rows of the old instrument leave the freeze: `results/runs_paper.csv`, `results/web_benchmarks.json` and `results/generated` are regenerated from the new rows alone. Nothing of the old instrument stays beside them, no second freeze, no second payload, no second route.

Run `campaign_switch_check.py --new-pin <pin>` first. It changes nothing: it reports which tracked files still name the old pin, and which documentation lines name a version, a date, an issue number, or an instrument label, since those are prose no generator keeps current.

Then, in order: land the final stage and freeze; run every gate on the new payload, including the manifest coverage check; publish with `refresh_web_page.py`; publish the results asset; update the files the check listed that are not historical mentions; update the documentation lines it listed that the new instrument changes; and rebuild both sites, checking that the page's link to the docs and the docs' links to the page still resolve.

Pruning comes before the documentation pass, and the documentation pass is not optional: removing a rule leaves sentences elsewhere that referred to it, and a document describing something that no longer exists is worse than no document. The check is a report rather than a gate on purpose: a file naming the old pin may be recording history rather than describing the present, and a tool that decided that for you would be wrong in both directions.

## The "Run it yourself" guide at a landing

`docs/reproduce.md` names the ArcadeDB wheel of the published rows (`arcadedb-jvm==<version>`), the packages of `build_images.sh`, and a table of the time and memory of the small cells that `tools/small_cell_cost.py` prints from `results/runs_paper.csv`. A landing that moves the engine version or the rows changes the guide in the same pull request: `test_reproduce_guide.py` fails otherwise and prints the table to paste. The weekly `reproduce-smoke.yml` runs the guide's e2 cell from the blocks it marks as runnable.
